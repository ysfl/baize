# AI 接入与远程任务使用指南

[返回 README](../README.md)

这份指南写给使用白泽的 AI 助手、自动化工具，以及把 AI 纳入运维流程的管理员。推荐先安装白泽 AI 接入组件，让 AI 通过本机 Baize MCP 按需读取白泽信息；需要解释、部署、升级、恢复或高级集成时，再回到本指南和公开 API。远程写操作仍须由白泽现有权限和人工确认流程负责。

## 推荐接入路径

1. 运行 [`scripts/install-ai-access.sh`](../scripts/install-ai-access.sh)，或在 Windows 使用 [`scripts/install-ai-access.ps1`](../scripts/install-ai-access.ps1)。这两个脚本只安装 MCP 与 Skill，不安装白泽中心服务、控制台或 Agent；产品安装仍使用 [`scripts/install.sh`](../scripts/install.sh)。
2. 在本机交互式终端运行安装器提示的 `baize-mcp login`，密码不会进入命令参数或 AI 对话。
3. 重新打开 AI 客户端。已安装的公开 Skill 会把“查节点、看状态、找异常”等自然语言意图优先路由到 Baize MCP。
4. AI 先调用 `baize_connection_status`，再按名称、别名、系统、地区、版本、架构、状态或分组调用 `baize_agents_list`；唯一匹配后才调用 `baize_agent_get`。用户不需要记住节点 ID。
5. 需要远程动作时，先用命令模板列表和模板预览确认可用范围，再创建命令计划。创建计划不会直接派发；执行或取消前必须得到操作者明确确认。

## 更新 MCP 与 Skill

AI 接入组件与白泽产品独立更新。已经安装过 MCP 和 Skill 的用户，在原来通过 Git 获取的 `baize` 目录中运行：

```bash
bash scripts/upgrade-ai-access.sh --lang zh
```

Windows 使用 `scripts/upgrade-ai-access.ps1`。升级器会先快进更新公开接入入口，再按当前正式发布安装 MCP、校验下载包与运行文件，并同步公开 Skill。它会拒绝覆盖包含本地修改的目录；升级不会删除或重新要求已有的本机登录会话。升级前请退出正在使用 MCP 的 AI 客户端，升级完成后再重新打开，使新的工具定义生效。

如果用户是手动从 [Baize MCP Releases](https://github.com/ysfl/baize-mcp/releases) 解压安装，则可以重新运行公开 AI 接入安装器，或下载目标版本覆盖同一目录并保留随包提供的 `baize-mcp.sha256`；不要删除本机配置目录或凭据存储。

## 四层分工

| 组件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 公开 API | 提供稳定的能力和字段，供高级集成使用 | 不负责替代 AI 客户端的工具发现和自然语言编排 |
| Baize MCP | 把已发布能力变成 AI 可发现、可传参的本地工具，并控制结果大小；支持模板预览、计划管理和任务状态 | 不复制白泽权限、不保存秘密、不提供万能请求转发 |
| Baize AI Skill | 判断何时使用白泽、选择 MCP 工具、处理唯一/多/零匹配和降级 | 不复制完整 API 文档，也不自行执行未公开动作 |
| 公开文档 | 说明安装、升级、排障、人工恢复和高级用法 | 不要求每次对话重新粘贴登录信息 |

当 MCP 和 Skill 都可用时，MCP 优先；当 MCP 不可用时，先修复本机接入，再阅读文档；只有 MCP 未覆盖且用户明确需要时，才使用公开 API。

## 基本原则

| 原则 | 要求 |
| --- | --- |
| 人先确认 | AI 在创建计划前先展示目标、模板、参数、风险和预期结果；在执行或取消远程任务前，必须让操作者明确确认。 |
| 只读优先 | 能用只读诊断完成的，不先做修改。优先查看状态、日志、磁盘、端口、进程和服务信息。 |
| 使用白泽入口 | 涉及被纳管服务器的操作，应通过白泽控制台里的远程任务、命令计划、服务管理或文件分发完成，不绕过白泽审计。 |
| 最小范围 | 先单台验证，再小批量执行，最后再扩展到更多服务器。不要一开始就全量执行。 |
| 风险停顿 | 遇到重启、删除、权限变更、防火墙、账号、批量操作等高风险动作，必须停下来等待人工确认。 |
| 结果留痕 | 每次任务都要有清晰标题、目标、原因、预期结果、执行结果和后续动作，方便在审计里回看。 |

## 开始前需要用户确认的信息

AI 应先判断 Baize MCP 是否已经连接。连接可用时，不要再次向用户索取白泽地址、登录账号、密码、会话或节点 ID；先通过 MCP 查询候选。远程任务不是让 AI 自行拼接白泽服务路径，也不是让 AI 直接 SSH 到目标服务器；当前 MCP 没有覆盖的操作应回到白泽控制台。

| 信息 | 要求 |
| --- | --- |
| 连接状态 | 先调用 `baize_connection_status`。会话有效时直接继续；失效时引导用户回到本机终端重新登录，不在对话里询问连接地址。 |
| 登录用户 | MCP 使用本机已经登录的白泽账号及其权限范围。需要更换账号时，由用户在本机终端重新登录。 |
| 登录密码 / 会话 | 不把密码、会话或地址贴进聊天。登录由用户在本机交互式终端完成，会话由系统凭据存储保护。 |
| 安全码 / 二次确认 | 安全码、审批、二次确认必须由具备权限的操作者完成。AI 不应要求用户把安全码长期暴露在对话里，也不得建议跳过。 |
| 目标 Agent | 先按用户给出的名称或业务特征查询。唯一匹配时只在后续工具调用中使用 ID；多个匹配时展示候选让用户选择；没有匹配时继续询问特征。 |
| 操作人 | 只读查询不要求重复声明；准备远程写操作时必须明确负责人。AI 只能作为助手，不能把自己写成最终操作责任人。 |
| 维护窗口 | 只在服务重启、升级、批量操作或配置变更时确认允许执行的时间段。 |

如果当前客户端没有 MCP 工具，先按推荐接入路径安装或修复接入。只有写操作所需信息缺失时，AI 才向用户补问，不要把只读查询变成一轮配置问答。

## MCP 命令工作流

当用户要求执行白泽已提供的命令工作流时，AI 应按以下顺序操作：

1. 使用 `baize_command_templates_list` 找到当前账号可用的模板，先确认模板名称、参数约束、平台和风险等级。
2. 使用 `baize_command_template_preview` 对已选节点进行预览和预检。预览不会创建计划或运行命令；不展示或索取模板命令正文之外的秘密参数。
3. 向操作者展示目标节点、模板、参数、风险、预检结果、预期结果和回滚方式。多个节点或多个模板匹配时必须先让用户选择。
4. 用户确认创建后，使用 `baize_command_plan_create` 创建计划，再使用 `baize_command_plan_get` 复核计划状态、风险和预检结果。创建计划本身不会派发任务。
5. 只有用户再次明确确认执行后，才使用 `baize_command_plan_execute`。白泽可能要求风险确认、审批或二次安全确认；必须按返回结果处理，不绕过。
6. 使用 `baize_exec_task_get` 查询整体及目标进度。需要停止等待中或运行中的任务时，先说明影响，再在用户确认后使用 `baize_exec_task_cancel`。

MCP 只返回有限的计划和任务状态字段，不返回命令正文、工作目录、环境变量、操作者身份或任务输出。需要查看完整审计和输出时，回到白泽控制台。

## 任务元数据要求

每个远程任务都应让用户能在审计里看懂“谁、在什么时候、为了什么、对哪些服务器做了什么”。AI 生成任务草案时，应包含这些字段：

| 字段 | 要求 |
| --- | --- |
| 任务标题 | 简短说明场景、目标和动作，例如 `排查 Nginx 端口监听 - web-01 - 只读`。不要使用 `test`、`临时执行`、`修一下` 这类标题。 |
| 任务类型 | 明确是只读诊断、服务操作、文件分发、批量命令、Agent 检查、Agent 升级或其它类型。 |
| 操作人 | 写明发起人或负责人；如果 AI 代为整理草案，仍应记录真实操作者。 |
| 目标范围 | 写明 Agent ID、Agent 名称或分组，以及目标数量。批量任务还要写明批次大小。 |
| 操作原因 | 写明来自告警、用户请求、维护计划还是故障排查。 |
| 命令内容 | 展示完整命令或脚本草案，不用“执行上面的命令”等模糊描述。 |
| 工作目录 | 使用明确目录；不确定时使用安全的默认目录，或先执行只读检查确认。 |
| 超时时间 | 按任务类型设置，不使用无限等待。 |
| 风险等级 | 至少区分低、中、高；删除、重启、权限、防火墙、批量操作默认按高风险处理。 |
| 回滚方式 | 写明失败后如何停止、恢复或回看；没有回滚方式时必须提示用户风险。 |

任务标题推荐格式：

```text
<场景> - <目标> - <动作>
```

示例：

```text
排查磁盘占用 - web-01 - 只读
重载 Nginx - web 分组第一批 - 需确认
检查 Agent 状态 - prod-db-01 - 只读
```

## 推荐流程

1. **确认连接与身份**

   先用 MCP 检查已保存会话。只读查询直接使用当前账号权限；写操作再确认操作人和维护窗口。

2. **确认目标**

   先用节点列表按名称或业务特征查询。唯一匹配时继续，多个匹配时请用户选择，没有匹配时询问更多特征。目标不清楚时，不创建任务。

3. **收集只读信息**

   优先使用状态查看、日志尾读、进程查看、端口查看、磁盘查看等只读命令。示例：

   ```bash
   systemctl status <service-name> --no-pager
   journalctl -u <service-name> -n 100 --no-pager
   ss -lntp
   df -h
   free -m
   ```

4. **给出任务草案**

   AI 应先展示任务草案，而不是直接执行。草案至少包含：

   - 接入方式（已连接 MCP 或白泽控制台）
   - 操作人
   - 目标服务器或分组
   - 已确认的目标名称或筛选条件
   - 任务标题
   - 操作目的
   - 命令或任务类型
   - 工作目录
   - 超时时间
   - 预期输出
   - 风险说明
   - 回滚或停止方式

5. **由操作者确认**

   操作者在白泽控制台确认后，再创建或执行任务。如果控制台提示二次确认、安全码或审批，AI 不得建议绕过。

6. **观察执行结果**

   任务开始后，关注状态、输出、失败目标和超时目标。不要因为某台失败就盲目重复执行；应先判断失败原因。

7. **记录结论**

   任务结束后，AI 应总结执行结果、失败原因、受影响服务器和下一步建议。敏感输出要先脱敏再进入对话或工单。

## Agent 相关操作

白泽 Agent 负责采集和执行远程任务。对 Agent 本身做操作时要更谨慎，因为它也是任务执行链路的一部分。

| 场景 | 建议 |
| --- | --- |
| 查看 Agent 状态 | 可以先用只读命令查看服务状态和最近日志。 |
| 重启 Agent | 只在明确需要时执行，并先确认任务输出可能中断、状态可能短暂超时。 |
| 升级 Agent | 优先使用白泽控制台提供的升级能力，不手写自升级脚本。 |
| Agent 离线 | 不要继续派发远程任务；先排查网络、注册令牌、服务状态和服务器防火墙。 |
| 批量 Agent 操作 | 先选 1 台验证，再按小批次推进，并保留失败停止条件。 |

常用只读检查示例：

```bash
systemctl status baize-agent --no-pager
journalctl -u baize-agent -n 100 --no-pager
ps -ef | grep baize-agent | grep -v grep
```

如果服务器不是 systemd 环境，应按实际安装方式查看 Agent 进程和日志，不要把上面的命令硬套到所有系统。

## 命令要求

AI 生成远程任务命令时，应遵守这些要求：

- 命令尽量可重复执行，重复执行不会造成额外破坏。
- 使用明确路径，避免依赖未知的当前目录。
- 不把密码、令牌、私钥、证书私钥写进命令或参数。
- 不把大量日志完整输出到任务结果里，优先限制行数或时间范围。
- 长任务必须设置合理超时。
- 批量任务必须限制并发，并准备失败停止条件。
- 写操作前先做只读检查，确认目标存在且状态符合预期。
- 修改配置前先备份或确认白泽已有可回看的变更记录。
- 对用户输入、路径、服务名、文件名使用明确参数，不把未经确认的文本直接拼进 shell。

## Shell 符号安全

很多远程任务事故不是命令本身危险，而是 shell 符号组合错误导致命令穿透、条件失效或范围扩大。AI 生成命令时应特别注意：

| 符号或写法 | 风险 | 要求 |
| --- | --- | --- |
| `;` | 前一条失败后仍继续执行后一条 | 只有步骤彼此独立时才用；有依赖关系时优先用 `&&`。 |
| `&&` | 只在前一条成功后继续 | 适合“检查通过后再执行”的链路。 |
| `||` | 失败后执行兜底命令，容易把高风险命令放进失败分支 | 兜底动作必须低风险，并用括号或明确结构限定范围。 |
| `|` | 管道可能隐藏左侧命令失败 | 关键任务不要只依赖管道最后一段结果；必要时拆开检查。 |
| `&` | 后台执行会让任务提前返回，输出和失败可能不可见 | 只在明确需要后台执行时使用，并写明日志路径和检查方式；不要写出 `&;` 这类错误组合。 |
| `>` / `>>` | `>` 会覆盖文件，`>>` 会追加到文件 | 写入前必须确认目标路径，避免覆盖配置或系统文件。 |
| `2>&1` | 重定向顺序错误会让输出落到非预期位置 | 日志重定向要写清楚，例如 `command > /tmp/task.log 2>&1`。 |
| `*` / `?` / `[]` | 通配符可能匹配过多文件 | 删除或移动文件时避免宽泛通配；必须先 `ls` 或 `find` 只读确认范围。 |
| `` `...` `` / `$(...)` | 会执行子命令 | 不要把用户输入放进命令替换里。 |
| 引号 | 未加引号的变量可能被空格、通配符或分号拆开 | 路径和变量必须加双引号，例如 `"$target_path"`。 |
| 换行 | 多行脚本中换行可能改变条件作用范围 | 多行脚本要按完整脚本审查，不要把片段随意拼接。 |
| `eval` | 会二次解释字符串，极易造成命令注入 | 禁止在 AI 生成的远程任务中使用。 |

更安全的写法方向：

```bash
# 只读检查先行
test -d "/var/log/nginx" && du -sh "/var/log/nginx"

# 有依赖关系时使用 &&
systemctl status nginx --no-pager && journalctl -u nginx -n 100 --no-pager

# 清理前限定目录并先展示范围
find "/tmp/my-app-cache" -maxdepth 1 -type f -mtime +7 -print
```

高风险或不推荐写法：

```bash
# 前面失败也会继续 reload
nginx -t; systemctl reload nginx

# 路径为空或变量异常时可能扩大删除范围
rm -rf $target_path/*

# 二次解释用户输入，容易形成命令穿透
eval "$user_command"
```

如果确实需要执行写操作，应把只读确认和写操作拆成两个任务：先让用户看见影响范围，再由用户确认第二个任务。

## 高风险动作

以下动作必须由管理员明确确认；AI 不应把它们作为默认建议：

| 动作 | 要求 |
| --- | --- |
| 重启业务服务 | 确认维护窗口、影响范围和恢复检查方式。 |
| 删除文件或清理目录 | 只允许清理明确的业务缓存、临时文件或日志片段；必须写清路径和匹配范围。 |
| 修改账号、权限或 SSH 配置 | 必须确认备用登录方式，避免把自己锁在服务器外。 |
| 修改防火墙或安全策略 | 必须确认放行规则和回滚方式，避免切断控制台或 Agent 连接。 |
| 批量执行 | 先单台验证，再小批量，最后扩大范围。 |
| Agent 重启或升级 | 优先使用白泽内置流程，并准备连接中断后的观察方式。 |

以下动作不应通过 AI 远程任务执行：

- 格式化磁盘、重写分区表、擦除块设备。
- 删除根目录、系统目录或未限定范围的大目录。
- 清空防火墙规则。
- 输出或打包密码、令牌、私钥、证书私钥。
- 在没有备份和回滚说明的情况下修改生产配置。

## 批量任务规范

批量任务最容易把小问题放大。AI 应按下面方式推进：

1. 先选择 1 台低风险服务器验证命令。
2. 选择 2 到 5 台同类服务器做小批次。
3. 明确失败停止条件，例如任意一台失败就暂停，或失败率超过阈值就暂停。
4. 每一批结束后读取结果，再决定是否继续。
5. 不把不同操作系统、不同业务角色、不同网络区域的服务器混在一个批次里。

## 输出与隐私

远程任务输出可能包含路径、用户名、进程参数、内部地址或业务日志。AI 在使用输出时应做到：

- 只摘录和问题相关的片段。
- 对密码、令牌、私钥、会话、手机号、邮箱等敏感内容脱敏。
- 不把完整日志贴到公开对话、公开工单或外部渠道。
- 需要长期留存时，使用白泽审计或你自己的内部归档方式。

## 失败处理

任务失败时，AI 应先定位原因，再建议下一步：

| 状态 | 建议处理 |
| --- | --- |
| 等待或运行时间过长 | 检查超时设置、命令是否需要交互、目标 Agent 是否在线。 |
| 超时 | 先查看已有输出，再决定是否取消、延长超时或拆分任务。 |
| 部分失败 | 只重试失败目标，并先确认失败原因一致。 |
| 输出过大 | 改用限制行数、时间范围或分页查看，不继续扩大输出。 |
| Agent 断连 | 暂停后续任务，先恢复 Agent 连接。 |

## AI 回复模板

AI 在建议远程任务前，可以使用下面的格式：

```text
接入方式：<已连接 MCP / 白泽控制台>
操作人：<负责人>
目标：<服务器或分组>
目标依据：<用户选择的名称或筛选条件>
任务标题：<场景 - 目标 - 动作>
任务类型：<只读诊断 / 服务操作 / 文件分发 / 批量任务 / Agent 操作>
目的：<要解决的问题>
命令草案：<命令或控制台任务配置>
风险等级：<低 / 中 / 高>
预期结果：<成功时应该看到什么>
失败处理：<失败或超时时怎么做>
需要你确认：<目标、维护窗口、是否允许执行>
```

只有在操作者确认后，才继续创建或执行远程任务。
